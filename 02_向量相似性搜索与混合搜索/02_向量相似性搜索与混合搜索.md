## 1. 章节简介

创建知识图谱可能是一个迭代的过程，你从非结构化数据入手，然后为其添加结构。当你拥有大量非结构化数据并希望开始利用这些数据来解答问题时，情况往往就是如此。

本章将探讨如何利用RAG技术基于非结构化数据进行问答。我们将学习如何通过向量相似性搜索和混合搜索来查找相关信息，以及如何运用这些信息生成答案。在后续章节中，我们还会研究在数据具备一定结构化特征时，可采用哪些技术来优化检索器和生成器，从而获得更优的结果。

在数据科学和机器学习领域，嵌入模型和向量相似性搜索是处理复杂数据的重要工具。本章将探讨如何用这些技术将文本和图像等复杂数据转化为名为嵌入向量（embedding） 的统一格式。

在本章中，我们将介绍嵌入模型和向量相似性搜索的基础知识，阐释它们为何实用、如何应用，以及它们在RAG应用中助力解决的挑战。要跟随本章节的实操步骤，你需要访问一个运行中的空白Neo4j实例。该实例可以是本地安装的，也可以是云托管的；只需确保其为空即可。你可以直接在配套的Jupyter Notebook中跟随实现步骤，访问地址为：https://github.com/tomasonjo/kg-rag/blob/main/notebooks/ch02.ipynb。

## 2. RAG 应用的组件

在RAG应用中，主要包含两个核心组件：检索器和生成器。检索器负责查找相关信息，生成器则利用这些信息生成回复。检索器中会运用向量相似度搜索来定位相关信息，这一技术会在后续内容中展开详细说明。接下来，我们将深入剖析这两个组件。

### 2.1. 检索器

检索器是RAG应用的第一个组件。其作用是查找相关信息并将这些信息传递给生成器。RAG应用并未规定检索器查找相关信息的具体方式，但最常用的方法是向量相似度搜索。我们来看看要让检索器借助向量相似度搜索高效工作，需要如何准备数据。

- **向量索引（VECTOR INDEX）**

虽然向量索引并非向量相似性搜索的严格必备条件，但强烈建议使用。向量索引是一种数据结构（类似映射），它以便于检索相似向量的方式存储向量。使用向量索引时，检索方法通常使用的是**近似最近邻搜索（approximate nearest neighbor search）**。这是因为向量索引无法找到精确的最近邻，而是能找到与最近邻非常接近的向量。这是在速度和精度之间做出的权衡。向量索引比暴力搜索快得多，但精度稍差。

- **向量相似性搜索函数（VECTOR SIMILARITY SEARCH FUNCTION）**

向量相似度搜索函数是一种以向量为输入并返回相似向量列表的函数。该函数可能会借助向量索引来查找相似向量，也可能采用其他（暴力）方法。关键在于它要返回一组相似向量。

两种最常见的向量相似度搜索函数是**余弦相似度（cosine similarity）和欧氏距离（Euclidean distance）**。欧氏距离体现了文本的内容和强度，在本书涵盖的大多数场景中并非那么重要。余弦相似度是衡量两个向量之间夹角的指标。在我们的文本嵌入场景中，这个夹角代表了两段文本在语义上的相似程度。余弦相似度函数接收两个向量作为输入，并返回一个介于 0 到 1 之间的数值；0 表示这些向量完全不同，1 则表示二者完全相同。余弦相似度被认为最适合文本聊天机器人，这也是我们将在本书中使用的指标。

- **嵌入模型（EMBEDDING MODEL）**

文本语义分类的结果称为 embedding 。想要使用向量相似性搜索匹配的任何文本都必须转换为 embedding。这是使用其嵌入模型完成的，重要的是嵌入模型在整个RAG应用程序中需要保持不变。如果要更改嵌入模型，则必须重新填充向量索引。

embedding 是一组数字列表，列表的长度被称为嵌入维度。嵌入维度至关重要，因为它决定了嵌入所能承载的信息量。嵌入维度越高，无论是生成嵌入还是执行向量相似性搜索，处理嵌入所需的计算成本就越高。

embedding 是一种将复杂数据表示为更简单、低维空间中一组数字的方式。可以将其理解为将数据转换为计算机能够轻松理解和处理的格式。

嵌入模型提供了一种统一的方式来表示不同类型的数据。嵌入模型的输入可以是任何复杂数据，输出则是一个向量。例如：在处理文本时，嵌入模型会将单词或句子转换为向量，而向量是由数字组成的列表。该模型经过训练，以确保这些数字列表能够捕捉到原始文本的核心特征，比如其含义或上下文信息。

- **文本分块（TEXT CHUNKING）**

文本分块是将文本分割成更小的片段的过程。这样做是为了提高检索器的准确性。更小的文本片段的存在意味着嵌入更窄、更具体；因此检索器在搜索时会找到更多相关信息。

文本分块非常重要，却又很难做好。你需要思考如何对文本进行拆分：是按句子、段落、语义，还是其他方式？应该使用滑动窗口，还是固定大小？分块的大小该如何确定？

这些问题没有标准答案，具体取决于使用场景、数据和领域。但重要的是要思考这些问题，并尝试不同的方法，为你的使用场景找到最佳解决方案。

- **检索器管道（RETRIEVER PIPELINE）**

一旦所有部分都准备好了，检索器管道就非常简单了。它将查询作为输入，使用嵌入模型将其转换为嵌入，然后使用向量相似性搜索函数来查找相似的嵌入。在天真的情况下，检索器管道然后只返回源块，然后将其传递给生成器。但是在大多数情况下，检索器管道需要做一些后处理来找到传递给生成器的最佳块。我们将在下一章讨论更高级的策略。

### 2.2. 生成器

生成器是检索增强生成（RAG）应用的第二个组件。它利用检索器找到的信息来生成回复。生成器通常是大型语言模型（LLM），但检索增强生成相较于微调或依赖模型基础知识的一个优势是，模型无需做得那么大。这是因为检索器会找到相关信息，因此生成器无需掌握所有知识。它确实需要知道如何利用检索器找到的信息来生成回复，而这一任务的难度远低于掌握所有知识。

因此我们利用语言模型生成文本的能力，而非其知识储备。这意味着我们可以使用更小的语言模型，其运行速度更快、成本更低。同时这也意味着我们可以确信，语言模型的回答将基于检索器获取的信息，因此其编造内容和产生幻觉的情况会更少。

### 3.2. 文本语料库

本示例中我们将使用的文本是一篇题为《爱因斯坦的专利与发明》（乔杜里，2017）的论文。尽管大语言模型对阿尔伯特·爱因斯坦了如指掌，但我们通过提出非常具体的问题，并将从论文中得到的答案与从大语言模型中得到的答案进行对比，以此展示检索增强生成（RAG）的工作原理。

### 3.3. 文本分块

当大语言模型拥有足够大的上下文窗口时，我们可以将整篇论文作为一个单独的文本块。但为了获得更好的效果，我们会将论文拆分成更小的文本块，以每数百个字符作为一个文本块。能产生最佳效果的文本块大小需根据具体情况而定，因此务必尝试不同的文本块尺寸。

在这种情况下，我们也希望分块之间存在一定重叠。这是因为我们需要能够找到跨多个分块的答案。因此，我们将使用一个大小为500个字符、重叠部分为40个字符的滑动窗口。这会使索引稍大一些，但也会让检索器的准确性更高。

为了让嵌入模型更好地对每个文本块的语义进行分类，我们将仅在空格处进行切分，这样每个文本块的开头和结尾就不会出现不完整的单词。该函数接收一段文本、块大小（字符数）、重叠长度（字符数），以及一个可选参数（指定是按任意字符切分还是仅按空格切分），并返回文本块列表。

```
def chunk_text(text, chunk_size, overlap, split_on_whitespace_only=True):
    """
    文本分块函数：保证不拆分单个单词，仅在空格处分割
    :param text: 原始长文本
    :param chunk_size: 分块目标长度
    :param overlap: 分块重叠长度
    :param split_on_whitespace_only: 是否仅按空白符分割（保证单词完整）
    :return: 分块后的文本列表
    """
    chunks = []
    index = 0

    while index < len(text):
        if split_on_whitespace_only:
            # 向左查找重叠区域内的最后一个空格
            prev_whitespace = 0
            left_index = index - overlap
            while left_index >= 0:
                if text[left_index] == " ":
                    prev_whitespace = left_index
                left_index -= 1

            # 向右查找目标位置后的下一个空格
            next_whitespace = text.find(" ", index + chunk_size)
            if next_whitespace == -1:
                next_whitespace = len(text)

            # 截取分块并清理首尾空格
            chunk = text[prev_whitespace:next_whitespace].strip()
            chunks.append(chunk)
            index = next_whitespace + 1
        else:
            # 非仅空格分割模式
            start = max(0, index - overlap + 1)
            end = min(index + chunk_size + overlap, len(text))
            chunk = text[start:end].strip()
            chunks.append(chunk)
            index += chunk_size
            break

    return chunks


# 调用示例：500字符分块，40字符重叠
chunks = chunk_text(text, 500, 40)
print(len(chunks))  # 输出总块数，示例：89 chunks in total
```

### 3.4. Embedding 模型

在选择嵌入模型时，重要的是要考虑你想要匹配的数据类型。在本例中，我们需要匹配文本，因此将使用文本嵌入模型。在本书中，我们会使用来自 OpenAI 的嵌入模型和大语言模型（LLMs），但市面上还有许多其他替代方案。Hugging Face 的 Sentence Transformers 中的 all-MiniLM-L12-v2（https://mng.bz/nZZ2）是 OpenAI 嵌入模型的绝佳替代方案，它使用起来非常简单，还能在本地中央处理器（CPU）上运行。

确定嵌入模型后，我们需要确保在整个RAG应用中都使用同一模型。这是因为向量索引填充的是来自该嵌入模型的向量，因此如果更换嵌入模型，就需要重新填充向量索引。若要使用OpenAI的嵌入模型对文本分块进行嵌入，我们可以使用以下代码。

```
# 定义文本块嵌入函数
def embed(texts):
    # 调用 OpenAI 嵌入模型生成向量
    response = open_ai_client.embeddings.create(
        input=texts,
        model="text-embedding-3-small"
    )
    # 提取并返回所有向量
    return list(map(lambda n: n.embedding, response.data))

# 对文本块进行嵌入，得到向量列表
embeddings = embed(chunks)

# 打印向量列表长度（与文本块数量一致）
print(len(embeddings))  # 89, matching the number of chunks

# 打印单个向量的维度
print(len(embeddings[0]))  # 1536 dimensions
```

正如我们在代码清单2.2中看到的，我们使用的嵌入模型输出的是1536维向量，因此在创建向量索引时，我们会将其用作维度数量。

```
driver.execute_query("""CREATE VECTOR INDEX pdf IF NOT EXISTS FOR (c:Chunk) ON c.embedding""")
```

我们将把向量索引命名为 pdf，它将用于通过余弦相似度搜索函数，根据 embedding 属性对 Chunk 类型的节点建立索引。

现在我们已经有了向量索引，就可以向其中填充嵌入向量了。我们将使用 Cypher 来完成这一操作，具体步骤是先为每个文本块创建一个节点，然后通过 Cypher 循环为该节点设置文本和嵌入向量属性。我们还会在每个:Chunk节点上存储一个索引，以便后续能够轻松找到对应的文本块。

```
cypher_query = '''
WITH $chunks as chunks, range(0, size($chunks)) AS index UNWIND index AS i
WITH i, chunks[i] AS chunk, $embeddings[i] AS embedding
MERGE (c:Chunk {index: i}) SET c.text = chunk, c.embedding = embedding
'''
driver.execute_query(cypher_query, chunks=chunks, embeddings=embeddings)
```

要查看数据库中的内容，我们可以运行这条 Cypher 查询来获取索引为 0 的 :Chunk 节点。


## 4. 为 RAG 应用添加全文搜索以实现混合搜索

在上一节中，我们了解了如何利用向量相似度搜索来实现一个 RAG 应用。虽然纯粹的向量相似度搜索能发挥很大作用，也是对普通全文搜索的重大改进，但在实际生产场景中，它往往不足以保证足够高的质量、准确性和性能。

在本节中，我们将探讨如何改进检索器以获得更好的效果。我们还会研究如何在 RAG 应用中添加全文检索功能，以实现混合检索。

### 4.1. 全文检索索引

全文检索是数据库中的一种文本检索方法，已经存在很长时间。它通过关键词在数据中匹配内容，而非在向量空间中依据相似度进行匹配。在全文检索中要找到匹配结果，检索词必须与数据中的某个单词完全一致。

要实现混合搜索，我们需要在数据库中添加一个全文搜索索引。大多数数据库都有某种类型的全文搜索索引，在本书中我们将使用 Neo4j 的全文搜索索引。

```
driver.execute_query("CREATE FULLTEXT INDEX PdfChunkFulltext FOR (c:Chunk)
ON EACH [c.text]")
```

在这里，我们在:Chunk节点的text属性上创建一个名为PdfChunkFulltext的全文索引。

---

### 4.2. 执行混合搜索

混合搜索的思路是先进行向量相似度搜索和全文搜索，再合并结果。为了能对比两种不同匹配的得分，我们需要对得分进行归一化处理，具体做法是将每个搜索的得分除以该搜索的最高得分。

```
hybrid_query = '''
CALL {
	// vector index
	CALL db.index.vector.queryNodes('pdf', $k, $question_embedding) YIELD node, score
	WITH collect({node:node, score:score}) AS nodes, max(score) AS max UNWIND nodes AS n
	// Normalize scores
	RETURN n.node AS node, (n.score / max) AS score
	UNION
	// keyword index
	CALL db.index.fulltext.queryNodes('ftPdfChunk', $question, {limit: $k}) YIELD node, score
	WITH collect({node:node, score:score}) AS nodes, max(score) AS max
	UNWIND nodes AS n
	// Normalize scores
	RETURN n.node AS node, (n.score / max) AS score
}
// deduplicate nodes
WITH node, max(score) AS score ORDER BY score DESC LIMIT $k
RETURN node, score
'''
```

我们编写一条联合 Cypher 查询，先执行向量相似度搜索，再执行全文搜索。随后对结果进行去重，并返回前 k 个结果。

```
similar_hybrid_records, _, _ = driver.execute_query(hybrid_query, question_embedding=question_embedding, question=question, k=4)
for record in similar_hybrid_records:
    print(record["node"]["text"])
    print(record["score"], record["node"]["index"])
    print("======")
```

## 5. 章节总结

在本章中，我们探讨了向量相似性搜索的定义、组成部分，以及它如何融入RAG 应用中。随后，我们添加了全文搜索功能以提升检索器的性能。

同时结合向量相似度搜索和全文搜索，比仅使用其中一种方法能获得更好的结果。尽管这种方法在特定场景下可能效果良好，但由于我们是利用非结构化数据来检索信息，混合搜索的质量、准确性和性能仍存在较大局限。文本中的引用信息未必能被完整捕捉，而上下文内容也往往不足以让大语言模型理解文本含义，进而生成优质答案。

在下一章中，我们将探讨如何改进检索器以获得更好的结果。

- RAG 应用程序由检索器和生成器组成。检索器查找相关信息，生成器利用这些信息生成回复。
- 文本嵌入在向量空间中捕捉文本的含义，这使我们能够利用向量相似性搜索来查找相似的文本。
- 通过在RAG应用中添加全文搜索功能，我们可以启用混合搜索来提升检索器的性能。
- 向量相似性搜索和混合搜索在特定场景下能发挥良好作用，但随着数据复杂度的提升，它们的质量、准确性和性能仍存在较大局限。
